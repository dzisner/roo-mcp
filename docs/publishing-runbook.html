One-time setup

Done once per operator machine. Skip this section on subsequent releases.

  1. npm account

    Create at npmjs.com/signup. Consider enabling 2FA in your npm settings; it applies to npm publish too and prevents accidental releases from a compromised session.

  2. Log in from this machine

    > npm login

    Opens a browser for OAuth. Verify with:

    > npm whoami
# → your-npm-username

  3. Git identity

    Required for the release commit. Set once, globally:

    > git config --global user.name  "Your Name"
> git config --global user.email "you@example.com"

  4. GitHub remote

    The repo already exists locally. Point it at the GitHub URL and push the initial commit:

    > git remote add origin https://github.com/<you>/roo-mcp.git
> git push -u origin main

Release a version

The full cycle for every release, small or large. Runs in ~1 minute end-to-end.

  1. Preflight — nothing uncommitted, tests green

    > git status                    # must be clean
> npm run typecheck             # zero errors
> node scripts/verify-har-fixture.mjs   # SUBSET PASS
> node scripts/smoke.mjs        # every tool, real API
    Why smoke

    The prepublishOnly hook only runs typecheck + build. It does NOT hit Roo's API. Skip smoke at your peril: it's the only automated check that the tools actually work end-to-end.

  2. Preview what will ship

    > npm publish --dry-run

    Confirms the tarball contents (LICENSE, README.md, and everything under dist/) and that the version is what you expect. No writes to the registry.

  3. Bump the version

    Use the right bump for the change (see Versioning policy):

    > npm version patch     # 0.1.0 → 0.1.1
> npm version minor     # 0.1.0 → 0.2.0
> npm version major     # 0.1.0 → 1.0.0

    This edits package.json, commits the bump, and creates a matching vX.Y.Z git tag.

  4. Publish

    > npm publish

    The prepublishOnly hook runs typecheck + build automatically. If either fails the publish aborts before anything reaches the registry.

  5. Push the tag

    > git push
> git push --tags

Versioning policy

The tool interface is the public contract. Model names, input field names, and output field names decide the bump — internal refactors don't.

BumpWhenExamples
MAJOR Any change that breaks a caller who upgraded blindly. Renaming a tool (roo_set_smart_redirect → roo_set_click_count_redirect), removing a required input field, changing a response field's type.
MINOR Additive changes — new capability, existing callers unaffected. A new tool. A new optional input field. A new field in a response object.
PATCH Behavior-preserving fixes. The encodeRooId padded-id fix. A tightened error message. A dependency bump with no interface change.
Pre-1.0 caveat

While the version is 0.x.y, callers should expect that a MINOR bump may still contain a small breaking change if experience forces one. Once you're confident the tool surface is stable, ship 1.0.0 and treat the contract strictly from there.

Verify a release

Within a minute of npm publish the new version is fetchable. Confirm before telling anyone.

  1. Registry sees the new version

    > npm view roo-mcp version
# → 0.1.1  (or whatever you just published)

  2. A fresh npx install actually runs

    > npx --yes roo-mcp@0.1.1
# exits with "ROO_API_KEY is not set" — that's success

    Reaching the "key not set" message means npm found the tarball, downloaded it, and Node loaded dist/index.js. Any other failure — 404, module-not-found, syntax error — means the release is broken and needs a rollback.

Dogfood after publish

Point your own Claude clients at the published version instead of the local build. Catches any "works on my machine" bugs before users see them.

  1. Update Claude Desktop config

    Edit %APPDATA%\Claude\claude_desktop_config.json — swap the "command"/"args" pair:

    // before — local dev build
"roo": {
  "command": "node",
  "args": ["C:\\Users\\User\\Roo MCP\\dist\\index.js"]
}

// after — installed from npm
"roo": {
  "command": "npx",
  "args": ["-y", "roo-mcp"],
  "env": { "ROO_API_KEY": "your-key" }
}

  2. Same swap for Claude Code

    Edit ~/.claude.json, same JSON pattern under top-level mcpServers.roo.

  3. Fully quit and relaunch

    MCP servers are spawned at client startup — a new chat inside a running app won't pick up the change. Right-click tray → Quit for Desktop, or exit and re-launch claude for the CLI.

  4. Sanity-check in a chat

    Ask "check my Roo account". If roo_whoami returns the expected projection, the published tarball is running end-to-end.

Roll back a bad release

If the release is broken, the right move is almost always deprecate + patch forward, not unpublish.

Never npm unpublish a released version

npm allows it only within 72 hours, breaks the installs of anyone who already downloaded it, and blocks that exact version number forever. It should be reserved for cases where the tarball contains a leaked secret or credentials.

  1. Deprecate the bad version

    > npm deprecate roo-mcp@0.1.1 \
  "Buggy — please upgrade to 0.1.2+"

    The tarball stays installable, but every npm install/npx for that version prints the warning message. Users on it will notice; new installs of npx roo-mcp without a pinned version won't pick it up as long as a newer version exists.

  2. Fix the bug on main

    Land a fix like any other change. Add a smoke or regression test that would have caught it. Merge.

  3. Ship the patch

    Run the full release cycle from §2, bumping PATCH. The deprecation message auto-clears from user experience the moment they're on the new version.

Future: automate with CI

Manual publishing is fine at low frequency. Once releases are more than monthly, a GitHub Actions workflow that publishes on tag push is worth ~30 minutes of setup.

  1. Generate an npm automation token

    npmjs.com → your avatar → Access Tokens → Generate → Automation (does not require 2FA for CI). Copy the token — it's shown once.

  2. Add the token as a GitHub secret

    GitHub repo → Settings → Secrets and variables → Actions → New repository secret. Name NPM_TOKEN, value the token from step 1.

  3. Add the workflow

    Commit .github/workflows/release.yml:

    # .github/workflows/release.yml
name: release
on:
  push:
    tags: ['v*']
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          registry-url: 'https://registry.npmjs.org'
      - run: npm ci
      - run: npm run typecheck
      - run: npm publish
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

    After this lands, the manual publish workflow shrinks to: bump the version, push the tag, wait for the Action to go green.

Trade-off

Automation is only a real win once you'd otherwise ship several releases a month. Below that, the manual flow is faster than debugging a broken Action.
